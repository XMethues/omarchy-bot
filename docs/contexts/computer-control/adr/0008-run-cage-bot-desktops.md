# Run one pure-headless Cage Bot Desktop per Bot

Cage is the sole production compositor for Bot Screens. A Bot owns a Screen identity; its first graphical action or requested view provisions one pure-headless Cage Bot Desktop Session with a private Wayland socket, headless output, and persistent application surface. The runtime does not select another compositor, generate compositor configuration, bootstrap through the user's Wayland session, or start a full Omarchy session. Computer Preview is a low-frequency lossless PNG projection, Expanded Web Control is a WebRTC H.264 media track, and the HTTP PNG snapshot is a read-only fallback rather than a second live transport.

This supersedes the nested-Hyprland compositor and parent-Wayland mechanism in [ADR 0007](./0007-provision-nested-hyprland-per-bot.md). Bot-owned Surface identity, private sockets, headless outputs, independent pixels/focus/input, per-Screen coordination, targeted lifecycle cleanup, and the non-adversarial isolation boundary remain in force. [System ADR 0009](../../../adr/0009-share-work-files-isolate-bot-screens.md) clarifies on-demand lifetime and application ownership: per-Bot browser profiles or shared login behavior are not desktop product requirements, and disconnecting a viewer does not destroy its Bot's desktop.

The historical schema-v3 capacity report supports the existing admission configuration of four 1080p Screens and eight at 720p; eight 1080p Screens were unsupported in that matrix. Those results do not establish acceptable normal-use overhead or current Host Session safety. The [product acceptance requirements](../../../workspace-redesign.md#required-host-safety-and-resource-evidence) require selected-view measurements and explicit host top-bar/shortcut checks.

The processes still share the host Unix user, files, and permitted account resources. Private Wayland sockets prevent accidental routing but provide neither authentication nor an adversarial security boundary. Non-loopback HTTP and signaling remain explicitly unauthenticated and do not require HTTPS; H.264/WebRTC media encryption does not authenticate peer identity or make remote access secure.
